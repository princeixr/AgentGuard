# AgentGuard Multi-Agent Product Integration Plan

Last updated: 2026-06-06

## Goal

Turn the current single-fixture dashboard into a multi-agent AgentGuard control plane.

A signed-in AgentGuard customer should be able to:

1. create and register multiple agents,
2. integrate AgentGuard into each agent runtime,
3. see whether each integration is live or stale,
4. select one agent,
5. inspect only that agent's interceptions, sessions, traces, decisions, memory, and
   operational metrics,
6. manage that agent's policy and integration credentials,
7. later receive real Google ADK events through the same product APIs.

The key navigation model becomes:

```text
Signed-in user
    -> workspace
    -> agents
    -> selected agent
    -> live / replay / memory / operations / settings
```

## Current Problem

The existing system has `agent_id`, but it is not yet a product identity.

Today it is used inconsistently as:

- a hard-coded demo name,
- an ADK runtime name,
- a trace source field,
- a dashboard display value,
- an implicit storage namespace.

The current API routes are global:

```text
/api/v1/sessions
/api/v1/memory
/api/v1/operations/summary
/api/v1/events/stream
```

They read all records and do not establish ownership. A caller can submit an
`agent_id`, but there is no authenticated workspace or registered agent record proving
that the caller owns that identifier.

This must be corrected before integrating a real external ADK runtime.

## Identity Model

Use separate identifiers for control-plane ownership and runtime execution.

### Workspace

The tenant boundary for data, members, agents, policies, and API credentials.

```text
workspace_id: wsp_...
```

For the first demo there can be one seeded workspace and one local signed-in user, but
the boundary must exist in every record and API query.

### User

A human who logs into the AgentGuard dashboard.

```text
user_id: usr_...
```

Users access workspaces through memberships. Do not use the end user talking to an AI
agent as the dashboard `user_id`; those are different identities.

### Agent

The stable AgentGuard product record representing one logical customer agent.

```text
agent_id: agt_...
```

This is the common identifier used by all dashboard pages.

An `AgentRecord` should contain:

```text
agent_id
workspace_id
name
description
framework
status
created_at
created_by
default_policy_id
last_seen_at
metadata
```

`agent_id` is generated by AgentGuard and never chosen or trusted from arbitrary runtime
payloads.

### Deployment

One agent may run in development, staging, and production, or in several regions.

```text
deployment_id: dep_...
```

A deployment contains:

```text
deployment_id
agent_id
workspace_id
environment
runtime_framework
runtime_agent_name
version
status
last_seen_at
metadata
```

This replaces the current ambiguous use of `environment_id`, `runtime_agent_id`, and
`agent_config_id` as product identifiers. Those fields can remain as runtime metadata.

### Integration Credential

A secret used by the external agent runtime to authenticate to AgentGuard.

```text
integration_id: int_...
api_key_id: key_...
```

The plaintext key is displayed once. Only a secure hash is stored.

The credential is scoped to:

```text
workspace_id + agent_id + deployment_id + permissions
```

The ingestion API derives agent ownership from the credential. It must not accept an
untrusted request body as the authority for `workspace_id` or `agent_id`.

### Runtime Session

A single end-user interaction or agent execution.

```text
session_id: runtime-generated or AgentGuard-generated
```

Sessions belong to exactly one:

```text
workspace_id + agent_id + deployment_id
```

### End-User Subject

The person interacting with the customer's agent may be useful for correlation, but
AgentGuard should not require raw identity data.

Use an optional customer-generated pseudonymous value:

```text
subject_id_hash
```

Do not overload dashboard `user_id` with this field.

## Data Contract Changes

Add a common ownership envelope to live records:

```text
workspace_id
agent_id
deployment_id
integration_id
```

At minimum, add it to:

- `AgentGuardTraceV1.source`,
- `LiveEventV1`,
- `SessionRiskStateV1`,
- `GuardDecisionV1`,
- `TraceFeatureV1`,
- `GuardScoreV1`.

Recommended approach:

- keep the v1 record names,
- add optional ownership fields first for backward compatibility,
- make them required for all live ingestion endpoints,
- retain nullable fields only for historical fixtures and migration tools.

All records created from one interception must receive ownership from one trusted
`RuntimeIdentity` object rather than copying identifiers independently.

```python
RuntimeIdentity(
    workspace_id="wsp_...",
    agent_id="agt_...",
    deployment_id="dep_...",
    integration_id="int_...",
)
```

## Control Plane and Data Plane

Separate the two authentication paths.

### Control Plane

Used by humans in the dashboard:

- login,
- workspace membership,
- agent registration,
- credential creation/revocation,
- policy configuration,
- viewing traces and metrics,
- resolving approvals.

For the product demo, a local development login is acceptable. Keep authentication
behind an interface so a hosted identity provider can replace it later.

### Data Plane

Used by integrated agent runtimes:

- heartbeat,
- session registration,
- tool-call interception,
- tool result reporting,
- approval polling or streaming.

It authenticates with a scoped integration key, not a browser session.

## Agent Registration Flow

Create a new top-level **Agents** page.

### Agents List

Route:

```text
/agents
```

Show:

- agent name,
- framework,
- environment/deployment count,
- live/stale/offline status,
- sessions in the selected time range,
- intervention rate,
- last event time,
- integration health.

Actions:

- Register Agent,
- open agent,
- rotate/revoke credential,
- archive agent.

### Register Agent Wizard

Steps:

1. Name and describe the agent.
2. Select framework, initially Google ADK or Generic Python.
3. Create a deployment such as `development`.
4. Generate a one-time integration key.
5. Display framework-specific installation code.
6. Wait for a signed heartbeat.
7. Mark the integration live and open the agent dashboard.

Example future setup:

```python
from agentguard.integrations.google_adk import AgentGuardADK

guard = AgentGuardADK(
    api_url="http://localhost:8000",
    api_key=os.environ["AGENTGUARD_API_KEY"],
)

root_agent = Agent(
    ...,
    before_tool_callback=guard.before_tool_callback,
    after_tool_callback=guard.after_tool_callback,
    on_tool_error_callback=guard.on_tool_error_callback,
)
```

The integration key identifies the registered agent and deployment. The developer
should not need to hard-code `workspace_id` or `agent_id` in application code.

## Agent-Scoped Dashboard

Use nested routes:

```text
/agents
/agents/:agentId/live
/agents/:agentId/sessions
/agents/:agentId/replay/:sessionId
/agents/:agentId/memory
/agents/:agentId/operations
/agents/:agentId/settings
```

After an agent is selected, the application shell should show:

- agent name,
- environment selector,
- live status,
- last heartbeat,
- current policy.

The sidebar links must preserve `agentId`.

Do not keep global `/live`, `/memory`, and `/operations` as the primary routes. They
would make it too easy to display data from multiple agents accidentally.

An optional workspace-wide operations view can be added later, but it must be explicitly
named and aggregate agents intentionally.

## Agent-Scoped API

### Control Plane Routes

```text
GET    /api/v1/agents
POST   /api/v1/agents
GET    /api/v1/agents/{agent_id}
PATCH  /api/v1/agents/{agent_id}
POST   /api/v1/agents/{agent_id}/deployments
GET    /api/v1/agents/{agent_id}/deployments
POST   /api/v1/agents/{agent_id}/credentials
DELETE /api/v1/agents/{agent_id}/credentials/{credential_id}
```

### Dashboard Routes

```text
GET /api/v1/agents/{agent_id}/sessions
GET /api/v1/agents/{agent_id}/sessions/{session_id}
GET /api/v1/agents/{agent_id}/memory
GET /api/v1/agents/{agent_id}/memory/{trace_id}
GET /api/v1/agents/{agent_id}/operations/summary
GET /api/v1/agents/{agent_id}/operations/export
GET /api/v1/agents/{agent_id}/interceptions/current
GET /api/v1/agents/{agent_id}/events/stream
```

Every route must:

1. authenticate the dashboard user,
2. resolve workspace membership,
3. verify that the agent belongs to the workspace,
4. apply `workspace_id` and `agent_id` filters in the repository query.

### Runtime Routes

```text
POST /api/v1/runtime/heartbeat
POST /api/v1/runtime/sessions
POST /api/v1/runtime/interceptions
POST /api/v1/runtime/interceptions/{trace_id}/result
GET  /api/v1/runtime/interceptions/{trace_id}/approval
```

Runtime routes derive identity from the integration key.

## Repository and Elastic Changes

The current repository loads every record and filters in Python. That is acceptable for
fixtures but not for multi-agent data.

Repository methods should require a scope:

```python
AgentScope(
    workspace_id="wsp_...",
    agent_id="agt_...",
    deployment_id=None,
)
```

Examples:

```text
list_sessions(scope, filters)
get_session(scope, session_id)
search_memory(scope, filters)
operations_summary(scope, time_range)
stream_events(scope, cursor)
```

Elastic mappings must add keyword fields for:

```text
workspace_id
agent_id
deployment_id
integration_id
```

Every Elastic query must include workspace and agent filters. Document IDs should remain
globally unique, but authorization must never rely on uniqueness alone.

Local storage should move from a generic namespace to:

```text
data/runtime/<workspace_id>/<agent_id>/<deployment_id>/
```

Fixtures should seed at least two agents so accidental cross-agent reads are testable.

## Live Event Architecture

Replace the fixture-only `DemoRuntimeService` with a shared runtime event hub.

```text
ADK integration
    -> authenticated runtime interception endpoint
    -> firewall
    -> persistent records
    -> agent-scoped event hub
    -> /agents/{agent_id}/events/stream
    -> selected dashboard
```

The event hub key should be:

```text
workspace_id + agent_id + deployment_id
```

The deterministic runner should remain as a development integration that publishes
through the same runtime ingestion service. It should no longer have a separate product
path.

This is important: fixture and real ADK events must exercise the same API, storage, and
SSE code.

## Approval Model

Create a persisted `ApprovalRequest` record:

```text
approval_id
workspace_id
agent_id
deployment_id
trace_id
session_id
status: pending | approved | rejected | expired | cancelled
requested_at
expires_at
resolved_at
resolved_by
resolution_note
```

The dashboard resolves approvals through the control plane.

For the first real ADK integration:

- `allow` and `warn` return immediately,
- `block` returns a blocked tool response,
- `review` and `require_approval` create a pending approval,
- the runtime adapter waits only up to a configured timeout,
- approval executes the tool only if the ADK callback lifecycle can remain suspended,
- timeout or rejection returns a blocked/approval-required response.

Do not claim resumable approval until it is verified against the actual ADK callback
lifecycle. If callback suspension is unreliable, the honest first product behavior is
“request approval and retry,” not simulated continuation.

## Policy Scope

Policies should resolve in this order:

```text
workspace defaults
    -> agent policy
    -> deployment overrides
```

Each decision should record:

```text
policy_id
policy_version
effective_policy_source
```

This allows replay to explain which policy governed the action.

Policy editing can remain read-only during the first multi-agent milestone. Identity and
correct scoping are higher priority.

## Implementation Phases

### Phase A: Identity Foundation

- Add `WorkspaceRecord`, `UserRecord`, `MembershipRecord`, `AgentRecord`,
  `DeploymentRecord`, and `IntegrationCredentialRecord`.
- Add stable ID generation with `wsp_`, `usr_`, `agt_`, `dep_`, `int_`, and `key_`
  prefixes.
- Add a local control-plane repository.
- Seed one workspace, one user, and two agents.
- Add `RuntimeIdentity` and ownership fields to canonical records.
- Add cross-agent isolation tests.

Definition of done:

- two agents can produce records with no shared dashboard results,
- `agent_id` is generated by AgentGuard and is stable across deployments,
- runtime names are metadata rather than ownership identifiers.

### Phase B: Agent Registry API and Agents Page

- Implement agent, deployment, and credential APIs.
- Build `/agents`.
- Build registration wizard and integration instructions.
- Add heartbeat and live/stale/offline status calculation.
- Change the default route from `/live` to `/agents`.

Definition of done:

- a user can register an agent and deployment,
- a one-time integration credential is issued,
- heartbeat changes the agent to live,
- selecting an agent opens its scoped dashboard.

### Phase C: Scope Existing Dashboard

- Change all routes to `/agents/:agentId/...`.
- Add agent/environment context to the application shell.
- Refactor query service and repositories to require `AgentScope`.
- Add agent filters to local and Elastic repositories.
- Replace global SSE with agent-scoped SSE.
- Seed fixtures for two agents and verify isolation.

Definition of done:

- live, replay, memory, operations, export, and approvals only expose the selected
  agent,
- changing agents changes every page consistently,
- direct URL access cannot bypass ownership checks.

### Phase D: Unified Runtime Ingestion

- Implement runtime API-key authentication.
- Implement heartbeat, interception, result, and approval endpoints.
- Move firewall execution behind the runtime interception service.
- Make the deterministic runner call runtime ingestion APIs rather than reading fixture
  events directly.
- Publish stored events through the shared event hub.

Definition of done:

- deterministic and external runtimes use the same code path,
- the dashboard displays events immediately after ingestion,
- no product route depends directly on `DemoRuntimeService`.

### Phase E: Google ADK SDK Integration

- Extract ADK callbacks from `apps/adk_agent/agent.py` into a reusable integration
  package.
- Authenticate with an AgentGuard integration key.
- Send heartbeat and tool proposals to runtime APIs.
- Report executed/failed tool results.
- Implement and verify approval timeout behavior.
- Use the registered `agent_id` derived from credentials.

Definition of done:

- a separate Google ADK process appears as live on the Agents page,
- its real tool proposals appear under the correct agent,
- decisions are enforced before tool execution,
- execution results update replay and operations,
- another agent cannot read or publish into its data.

### Phase F: Authentication and Hosted Hardening

- Replace local development login with a hosted identity provider.
- Add secure cookie sessions or validated JWTs.
- Store credential hashes and support rotation/revocation.
- Add workspace roles: owner, admin, operator, viewer.
- Add rate limits, audit events, retention rules, and secret redaction.

This phase is required before calling the system enterprise-ready, but it should not
block the local multi-agent and real ADK demo.

## Recommended Next Step

Implement only Phase A first.

Do not connect Google ADK to the current global API. Doing that now would bake an
untrusted and ambiguous `agent_id` into ingestion, storage, SSE, and approvals.

The first code change should establish:

```text
workspace -> agent -> deployment -> runtime identity -> scoped records
```

Once that boundary is tested with two fixture agents, build the Agents page and then
route Google ADK through the unified runtime ingestion path.
